# 開発の進め方

**このリポジトリの第一の目的は「開発の進め方を洗練させること」で、アプリはその題材。**
だから実質の本体はこのファイル。形が固まったら、リポジトリの外に持ち出して使い回す。

---

## 1. 全体の流れ

```
Why  →  イベントストーミング  →  BDD  →  DDD  →  TDD
         （発見する）        （振る舞いを   （言葉と    （作る）
                             決める）     ルールを
                                         型にする）
ADR は随時。判断が出たらその場で書く。「捨てたもの」を必ず書く。
```

前の段を完璧にしてから次へ、ではない。**行き来してよい。**
ただし最初の1回は、この順で通す。

| 段 | 答える問い | 正（せい）になるもの | 置き場 |
|---|---|---|---|
| Why | なぜ作るか。誰のどんな面倒か | 文章 | `docs/design/00-why.md` |
| イベントストーミング | 何が起きるか。どこで揉めるか | 付箋の表と図、用語集 | `event-storming/` |
| BDD | 外から見てどう振る舞うか | `.feature` | `features/` |
| DDD | 中の言葉とルールは何か | 型と不変条件のテスト | `api/src/domain/` |
| TDD | どう作るか | テストとコード | `api/` `web/` |

---

## 2. 何をどこに置くか

基準は2つ。

> **① 自動で検証できるものは、文書にしない。**
> **② 開発の流れに乗るものは直下、乗らないものは `docs/`。**

文書は放っておくと静かに古くなる。テストは古くなると落ちる。**落ちれば気づける。**
だから「気づけない形」で持つものを最小にする。

```
pickup-planner/
├── event-storming/   ① 発見する      ─┐
├── features/         ② BDD            │ 正。開発の流れの順に並ぶ
├── api/              ③ DDD + ④ TDD    │
├── web/                               ─┘
└── docs/             開発の流れに乗らない文書の格納庫
    ├── README.md     このファイル
    ├── design/       設計書（初見の人の入口。正から抽出する）
    └── adr/          決めたことと、捨てたもの
```

動画の台本・スライドは、ここには置かない。`CONTRIBUTING.md` の7を見る。

### 設計書（`docs/design/`）は「抽出物」

イベントストーミングの付箋や Gherkin は、初見の人には読みにくい。
だから**正から抽出した読み物**を `docs/design/` に置く。

| ファイル | 中身 | 抽出元 | 従来の工程 |
|---|---|---|---|
| `00-why.md` | ペイン、肩代わりすること、やらないこと | **抽出元なし。手で書く** | 企画 |
| `01-what.md` | 登場人物、ユースケース、ルール | `event-storming/` と Example Mapping | 要件定義 |
| `02-how.md` | 外から見た振る舞いの一覧、API の契約、画面の流れ | `features/`、API、ADR | 基本設計 |
| `03-domain.md` | 集約と境界の図 | `api/src/domain/` | 詳細設計の入口 |

守ること：

- **中身を持たない。要約と、正へのリンクだけ。**
- **手で直さない。** 正を直したら、設計書は作り直す（Claude に再抽出させてよい）。
- **その Day の動画のスライドの元にする。** 作る理由が2つあると、ずれたときに気づける。

**詳細設計を日本語の文書にしない。** 必ずコードとずれる。
型と、まだ実装のない関数と、テストの名前で書く。コンパイラが整合性を見てくれる。

## 3. 書く順番 ―― 横に広く1回、あとは縦に1本ずつ

```
            計画を作る  共有URL   同乗者入力  行程表を見る  再計算
  Why〜ES      ■         ■         ■          ■          ■   ← ここだけ横一列
  BDD          ■         ・         ・          ・          ・
  DDD/TDD      ■         ・         ・          ・          ・
  動作確認     ■         ・         ・          ・          ・
```

- **横 = 機能（ユースケース）の並び。縦 = 段の深さ。**
- Why とイベントストーミングだけ、横一列に全部やる。**全体像がないと1本目の選び方を間違える。**
- そこから下は**縦に1本ずつ**。1本目が終わった時点で、粗いけれど**実際に使えるもの**が1つある。
- 縦切りは「設計が深くなる」で止めない。**実装して、動いて、確認できるところまで貫く。**

従来型（横に切る）は、全機能の基本設計が終わるまで動くものが1つもない。
個人開発だと、そこに到達する前に飽きる。

## 4. イベントストーミング ―― 何が起きるかを時系列に並べる

付箋の色を、Markdown の表の列で表す。図は Mermaid。

| 付箋 | 書き方 | 例 |
|---|---|---|
| **ドメインイベント**（橙） | 過去形 | 「乗車場所が登録された」 |
| **コマンド**（青） | 〜する | 「送迎計画を作る」 |
| **アクター**（黄・小） | 人 | 幹事、運転者、同乗者 |
| **ポリシー**（紫） | 〜したら〜する | 「期日の前日になったら再計算する」 |
| **読み取りモデル**（緑） | 誰かが見るもの | 行程表 |
| **外部システム**（ピンク） | 自分で作らないもの | Google Routes API、LINE |
| **集約**（黄・大） | ルールを守る単位 | 送迎計画 |
| **Hotspot**（赤） | 疑問・揉めどころ | 「積み込み時間は人ごとに違う？」 |

3段で進める。

1. **Big Picture**：イベントだけを、時系列に**全部**出す。順番や粒度は気にしない。
2. **Process Level**：イベントの間に、コマンド・アクター・ポリシー・読み取りモデルを足す。
3. **Design Level**：コマンドを受けてイベントを出す「ルールの塊」を見つける。**これが集約の候補。**

- 出てきた言葉は `event-storming/glossary.md`（用語集）に入れる。**以降の段は全部この言葉を使う。**
- **Hotspot は消さない。** `question` ラベルの Issue にする（CONTRIBUTING の 2）。

## 5. 要件を具体例に落とす ―― Example Mapping

ユースケース1つを4つに分解する。Issue のフォーム（`usecase`）がこの形。

| | 何を書くか |
|---|---|
| **ユースケース** | 誰が何をしたいか（1つ） |
| **ルール** | 守るべきこと（＝受け入れ条件） |
| **例** | 各ルールを説明する具体例。**これが `.feature` のシナリオになる** |
| **疑問** | 答えが出ていないこと。**消さない** |

### 要件の質を測る4つの判定

**これが Example Mapping の本当の値打ち。**

1. **ルールに例が1つも付かないなら、そのルールはまだ誰も理解していない。**
2. **例が2つあって同じルールを説明しているだけなら、片方は要らない。**
3. **どのルールにも当てはまらない例があるなら、ルールが抜けている。**
4. **疑問が多いユースケースは着手できない。** 見積りより先に、聞く相手を決める。

### 疑問（赤）は消さずに残す

**「ここは意見が割れている」を紙に出すことが一番効く。**
消してから進むと、どちらか片方の解釈が黙って実装される。
書くときは**「誰に聞けば答えが出るか」も一緒に**書く。

## 6. シナリオ（Gherkin）の書き方

`features/*.feature`。キーワードは3つだけ。

| キーワード | 意味 |
|---|---|
| **前提**（Given） | すでに成立している状況 |
| **もし**（When） | 起きた1つの出来事 |
| **ならば**（Then） | 期待する結果 |

```gherkin
# language: ja
機能: 運転者がお迎えの順番と時刻を決める

  背景:
    前提 積み込み時間は 5分 である

  シナリオ: 同乗者がいないとき、到着希望時刻から出発時刻を逆算する
    前提 出発点から目的地までの所要時間は 40分 である
    もし 運転者が到着希望時刻を 7:00 として送迎計画を作る
    ならば 出発時刻は 6:20 になる
```

**日本語で書く理由は1つだけ。非エンジニアが読めるようにするため。**
ここを英語やコードの言葉で書くと、ただの結合テストになる。

### 守ること4つ

1. **画面操作を書かない。** 「共有ボタンを押す」ではなく「同乗者に入力を依頼する」。
   UI の言葉で書くと、ボタンが動くだけで全部壊れる。
2. **数字を入れる。** 「適切な出発時刻が出る」は要件になっていない。
   **曖昧な言葉が残っているのは、まだ決まっていない証拠。**
3. **1シナリオ1主張。** `ならば` を並べたくなったら、シナリオが2本。
4. **用語集の言葉しか使わない。** シナリオの名詞がそのまま型名になるのが理想。

## 7. DDD ―― 言葉とルールを型にする

**ドメインモデルとは、業務のルールを TypeScript の型と関数で書いたもの。**
立派な文書ができるわけではない。できあがるのは3つ。

1. **用語集**（`event-storming/glossary.md`）。コードの名前もこれに合わせる。
2. **集約の図**（`docs/design/03-domain.md`。抽出物）。
3. **`api/src/domain/` の型と、不変条件のテスト。** ← これが正。

| 種類 | 何か | 例 |
|---|---|---|
| **集約** | ルールを守る単位。外からはここを通してしか変えない | 送迎計画 |
| **不変条件** | どんな操作のあとでも必ず成り立つこと。**テストになる** | 同じ同乗者を2回迎えに行かない |
| **値オブジェクト** | 中身が同じなら同じものとして扱う値 | 時刻、所要時間、地点 |
| **ポート** | ドメインから見た外の世界の口。中身は差し替えられる | 経路見積り（中身は Routes API） |

集約の候補は、イベントストーミングの Design Level でほぼ出ている。ゼロから考えない。

## 8. テストの割り振り

### BDD と TDD は入れ子

```
BDD（外のループ）：1ユースケース  ← 業務の言葉
   └─ TDD（内のループ）：1関数     ← コードの言葉
        赤（落ちるテストを書く）→ 緑（通す）→ 整える
   内が全部緑になると、外も緑になる
```

外側が「何を作るか」を決め、内側が「どう作るか」を決める。これを**アウトサイドイン**という。

### 受け入れテストと単体テストの境界

| | 受け入れテスト（外） | 単体テスト（内） |
|---|---|---|
| 確かめるもの | ユースケースが成立するか。つなぎ目も含む | 部品1つの正しさ |
| 言葉 | 業務の言葉（Gherkin） | コードの言葉 |
| 本数 | 少ない | 多い |
| 外部 | 偽物に差し替えて通す | そもそも触らない |

**異常系をどちらに書くかは「依頼者が知りたいか」で決める。**

| 例 | どちら |
|---|---|
| 到着希望時刻が過去なら作れない | **外**（仕様として合意が必要） |
| 同乗者0人でも成立する | **外**（起きうる使い方） |
| 住所が256文字を超えたとき | 内 |
| 積み込み時間の足し算の順序 | 内 |

**同じことを両方でテストしない。** 計算式そのものは単体テストで網羅し、
受け入れテストは「その計算式が呼ばれてユースケースとしてつながっている」ことだけ見る。

### 本数の形

```
     E2E（Playwright）        数本      ブラウザで本当に動くか
   受け入れ（Gherkin）       十数本     ユースケースが成立するか
    単体                     数百本     部品が正しいか
```

**逆三角形にすると死ぬ。** E2E ばかりだと、落ちても原因が分からず、遅いので誰も回さなくなる。
テストランナーは、足場の Day で ADR にして決める。

## 9. 型で消せるものは型で消す

| | 分かるタイミング | 網羅性 |
|---|---|---|
| **型** | 書いた瞬間 | **漏れがない**。ただし言えることが少ない |
| **テスト** | 動かしたとき | **書いた例しか見ない**。ただし何でも言える |

「ありえない状態を型で作れなくする」と、**テストが要らなくなる。**
たとえば「未来の時刻」だけを表す型を作り、それでしか送迎計画を作れないようにすると、
過去の時刻を渡したコードはコンパイルが通らない。テストが1本消える。

**型で消せるものは型で消し、消せないものだけテストで守る。**

## 10. 層の分け方が TDD と相性がいい理由

テストが遅い・不安定・準備が重い原因は、ほぼ全部**外の世界**にある。
ネットワーク、DB、**時計**、乱数、ファイル。

ドメイン層は外に触らない。だから**同じものを入れれば必ず同じものが出る。**
そこで**難しい判断を全部ドメイン層に集める。**
すると難しいところが全部、速くて壊れないテストで守られる。

層を分けないと、逆算のロジックが Google を呼ぶ関数の中に埋まる。すると：

- 「6:20 になること」を確かめるたびに Google を呼ぶ。テストが3秒かかる。
- ネットが落ちていると赤くなる。**自分のコードは正しいのに。**

**自分のコードが正しいのに落ちるテストは、人がすぐ信じなくなる。**
信じられないテストは無視され、無視されたテストは無いのと同じ。

| 層（`api/src/` の下） | 入れるもの |
|---|---|
| `domain/` | 判断と計算。**引数で全部もらう。I/O なし。NestJS も import しない** |
| `usecase/` | 手順の並び。外部は `interface`（ポート）越しにしか触らない |
| `infra/` | Google Routes API、DB |
| `presentation/` | NestJS のコントローラー。HTTP と、外に出す形への変換だけ |

**時計も「外の世界」。** ドメイン層に「現在時刻を取る」を書いた瞬間、
テストが実行時刻に依存して壊れる。現在時刻は引数で渡す。

`web/` は計算しない。API を呼んで表示するだけ。
フロントとバックの境目は、共有コードではなく **API の契約**で持つ。

### 診断に使える

> **テストが書きにくいと感じたら、層分けが間違っているサイン。**

「このテストを書くには DB を用意しないといけない」と思ったら、依存の向きが逆になっている。
**TDD はテスト手法というより、設計の間違いを早く教えてくれる装置。**

## 11. 読む順番

1. `docs/design/00-why.md` ―― なぜ作るか
2. `docs/design/01-what.md` → `02-how.md` → `03-domain.md` ―― 全体像（抽出物）
3. `event-storming/` ―― 何が起きるか（正）
4. `features/` ―― 実際に毎回検証される振る舞い（正）
5. `docs/adr/` ―― なぜそう決めたか（気になったときだけ）
