# 0001. GitHub Flow を使い、1 Day = 1 PR にする

- 日付: 2026-10-11
- 状態: 採用
- 関連: なし（着手時の決定）

## 状況

個人開発だが、**このリポジトリの第一の目的は、開発の進め方を業務に持ち込める形にすること。**
だから「1人だから省く」判断はしたくない。一方で、1人で回せない重さも避けたい。

前提：

- 開発者は1人。レビュー相手はいない。
- `main` にマージしたら Cloudflare と Cloud Run に自動で出す予定。
- 並行して保守するバージョンは存在しない。1つの本番だけ。
- BDD で進めるので、**受け入れ条件（ルールと例）を書く場所が必要。**
- 作る様子を **Day ごとに YouTube で公開する。** 1回分の区切りと、台本の材料が要る。

## 決定

**GitHub Flow を使う。** `main` と、短命の作業ブランチだけ。`develop` `release` は作らない。

そのうえで：

- **1 Day = 1 PR = 1本の動画。** Day は Milestone と親 Issue（タイトル `DayNN:`）で表す。
- ユースケース（`[UC]`）と疑問（`[Q]`）は、親 Issue の子にする。
- Issue のフォームで、**ルールと例を必須入力にする。**
- **1人でも PR を必ず通す。** CI を PR で回し、`Closes #N` で Issue と結ぶ。
- PR に「決めたこと／捨てたこと／次回の宿題」を書く。**これが台本の骨になる。**
- Issue の種類はタイトルの接頭辞で分かるので、ラベルは**タイトルで分からない状態**にだけ付ける。
  `question` と `adr-needed` の2つだけ。
- 議論は Issue、結論は ADR。双方向にリンクする。

手順の詳細は `CONTRIBUTING.md`。

## 検討して選ばなかったもの

- **1 Issue = 1 PR（前身リポジトリの形）。** 実装の Day はこれに近くなるが、
  イベントストーミングの Day は1つのユースケースに収まらない。
  Day を親にして、ユースケースを子にすることで両立させた。
- **Git Flow。** 並行保守するバージョンが無いので、重さに見合わない。

## 結果

できるようになること：

- Issue の受け入れ条件がそのままシナリオになり、シナリオがそのままテストになる。
- 各回が「前回の宿題（開いている `question`）」で始まり、「次回の宿題」で終わる。
  **動画の始まりと終わりが自然に決まる。**
- PR を見れば、その回で何を決めて何を捨てたかが分かる。

捨てたもの：

- **Git Flow の安全性。** リリースブランチを切って本番を固定する手が使えない。
- **`main` に直接コミットする速さ。** 1人なので純粋な手間だが、業務と同じ形にすることを優先した。
- **ラベルによる細かい分類。** 1人で維持できず、使われないラベルは嘘になる。
- **作業の切れ目を自由に決めること。** Day に収まるように作業を切る必要がある。

見直す条件：

- 本番を複数バージョン並行で保守する必要が出たとき（→ Git Flow を再検討）
- 1 Day に収まらない作業が続くとき（→ Day の切り方を先に見直す）
