# 0004. docs/ は「流れに乗らない文書」ではなく「段を横断する参照」の置き場

- 日付: 2026-10-15
- 状態: 採用
- 関連: [0003](0003-repository-layout.md)（`docs/` の定義を更新する）

## 状況

[0003](0003-repository-layout.md) では、`docs/` を「開発の流れに乗らない文書の格納庫」と定義した。
Day2 で `event-storming/glossary.md` を作ってみて、この定義では判断に迷う例が出た。

- 用語集は、イベントストーミングの段で生まれるが、**そのあと BDD・DDD・コードの命名でも
  ずっと引き続ける辞書。** 「ES の段の成果物」の1つとして `event-storming/` に置くと、
  あたかも ES だけのものに見えてしまう。
- 一方で、Why・ADR・設計書(`docs/`)も、生まれた段のあとまでずっと参照され続ける点は同じ。

**「流れに乗るか／乗らないか」ではなく、「段を横断して参照され続けるか／その段の作業の
成果物か」が、本当の分かれ目だった。**

## 決定

`docs/` の定義を、次のように更新する。

> **`docs/` は、段を横断してずっと参照され続ける文書の置き場。**
> Why・用語集・ADR・設計書(抽出物)が入る。

> **直下のフォルダ(`event-storming/` `features/` `api/` `web/`)は、その段固有の作業の成果物。**
> イベントストーミングの付箋・BDD のシナリオ・DDD/TDD のコードが入る。

これにより：

- `docs/language/glossary.md` に移す(`event-storming/glossary.md` から)。
  `language/` は `adr/` `design/` と並ぶカテゴリにした。今は1枚だが、将来
  コンテキストごとの用語差分などが増えても自然に収まる。
- `docs/` の中身は `design/`(Why・抽出物)・`language/`(用語集)・`adr/`になる。
- `event-storming/` には、その段固有の成果物(`big-picture.md` `process-level.md`)だけが残る。

「自動で検証できるものは文書にしない」という [docs/README.md](../README.md) の大元の基準は変えない。
用語集もイベントストーミングの付箋も、どちらも自動検証はされないが、**置き場所を分ける基準は
検証可否ではなく、参照され続ける範囲**だと整理した。

## 検討して選ばなかったもの

- **`event-storming/glossary.md` のままにする。** 「ES の段だけのもの」という誤解を招く。
- **`docs/glossary.md` に直接置く(フォルダを挟まない)。** `adr/` `design/` と並びが悪く、
  将来用語集まわりのファイルが増えたときに置き場所に迷う。
- **用語集を `event-storming/` にも `docs/` にも二重に置く。** 正が2つになり、ずれたときに
  どちらが正しいか分からなくなる。

## 結果

できるようになること:

- 「これは `docs/` か、直下か」を、**参照される範囲**という1つの基準で判断できる。
- 用語集が、ES だけでなく BDD・DDD でも引かれるものだと、置き場所から伝わる。

捨てたもの:

- 「流れに乗るか／乗らないか」という、[0003](0003-repository-layout.md) で立てた最初の基準。
  直感的だったが、用語集のような「生まれは1つの段、参照はずっと」というものを説明できなかった。

見直す条件:

- この基準でも判断に迷う文書が出てきたとき。
