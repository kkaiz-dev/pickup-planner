# 0003. 1サービス1リポジトリ。開発の流れに乗るものを直下に並べる

- 日付: 2026-10-11
- 状態: 採用
- 関連: なし（着手時の決定）

## 状況

決めたいことは2つ。

1. フロントと API を、リポジトリとしてどう分けるか。
2. イベントストーミング・シナリオ・コード・文書を、どこに置くか。

前提：

- フロントと API は、互いのコードに依存しない（[0002](0002-typescript-nestjs-svelte.md)）。
- 今後もサービスを作っていく。**どのサービスでも同じ形にしたい。**
- 1 Day = 1 PR で進める（[0001](0001-github-flow.md)）。1日の作業が複数のリポジトリに割れると困る。

## 決定

**1サービス = 1リポジトリ。** その中に、フロントと API を**互いに依存しない2つのサービス**として置く。
共通の workspace も、共通のコードも持たない。CI とデプロイも別々にする。

```
pickup-planner/
├── event-storming/   ① 発見する      ─┐
├── features/         ② BDD            │ 正。開発の流れの順に並ぶ
├── api/              ③ DDD + ④ TDD    │
├── web/                               ─┘
└── docs/             開発の流れに乗らない文書の格納庫
    ├── design/       設計書（正から抽出した読み物）
    └── adr/
```

- **開発の流れに乗るもの（正）は直下。** 直下を上から見れば、開発の順番が分かる。
- **`docs/` は「開発の流れに乗らない文書の格納庫」。** 「今の正」を置く場所ではない。
- **設計書（`docs/design/`）は抽出物。** 初見の人向けの入口で、正へのリンクを持つ。手で直さない。
- 単体テストは各サービスの中に置く。受け入れテストは `api/` の中から `features/` を読む。
- 空のフォルダは先に作らない。**それぞれ、初めて使う Day で作る。**

## 検討して選ばなかったもの

- **フロントと API でリポジトリを分け、外側のフォルダで包む。**
  イベントストーミングやシナリオをどちらに置くかが宙に浮く。
  1日の作業が複数のリポジトリの PR に割れる。
- **モノレポ（pnpm workspace などで共通コードを持つ）。** 共有するコードが無いので、仕組みだけが重くなる。
- **全部 `docs/` の下に入れる**（`docs/event-storming/` `docs/features/`）。
  イベントストーミングとシナリオは文書ではなく開発の一段なので、コードと同じ階層に置く。
- **フォルダ名に段の番号を付ける**（`01-event-storming/`）。行き来してよい段なので、順番は `docs/README.md` に書く。

## 結果

できるようになること：

- 1日の作業が1つの PR に収まる。
- あとでサービスを別のリポジトリに切り出すのは簡単（互いに依存していないので）。
- 次のサービスでも同じ形を使い回せる。

捨てたもの：

- **フロントと API の型の共有。** 境目は API の契約で持つ。契約がずれたら、どちらかのテストで気づく形にする。
- **リポジトリ単位で権限や公開範囲を分けること。** フロントだけ公開、のようなことはできない。

見直す条件：

- フロントと API を別の人（別のチーム）が持つようになったとき。
- 1つのサービスの中で、API を境界づけられたコンテキストごとに分けたくなったとき
  （→ `api/` を複数にするか、リポジトリを分けるかを、そのとき検討する）。
